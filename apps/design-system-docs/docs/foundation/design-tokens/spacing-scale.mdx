Background for the named steps in [Overview](./spacing.mdx). You do not use the primitive scale
directly, and it is hidden from the Figma variable picker, but you need it to understand why the
steps are the sizes they are and to make a case for adding one.

## The primitive scale

One scale, indexed so that **step `100` is 16px**. The index is hundredths of the 16px root, so the
px value is:

```
px = round(index × 0.16)
```

That is `25` for 4px, `100` for 16px, `200` for 32px. It is also why the low end has awkward names:
1px is `6`, not `1`.

:::note The rule only works in that direction
Rounding is lossy, so you cannot recover the index from the px. Four steps round into their
neighbours: 2px, 6px, 10px and 14px are `12`, `37`, `62` and `87`, not `13`, `38`, `63` and `88`.
Read the table rather than calculating backwards.
:::

### Two regions, at different resolutions

- **Below 16px** the steps are 1, 2, 3, 4, 6, 8, 10, 12 and 14px, so roughly 2px resolution. This is
  control-interior territory, and a 4px grid cannot pad a chip or offset an icon precisely enough.
- **From 16px up** it is a 4px grid to 64px, then 8px to 96px, then 16px to 352px. Layout territory,
  where precision below 4px is noise.

### Much of the scale is unused

Most primitive steps are pointed at by nothing, which the table above marks. Three things explain
the pattern:

- **The scale is shared with line height.** Eleven line-height primitives are aliases of spacing
  primitives, which is why `250` (40px) is in use even though no spacing step is 40px.
- **The layout steps reach further up than the component steps.** `4xl` through `6xl` are what
  point at `275` through `900`. Before they were added, nothing above 40px was referenced at all.
- **The top of the scale is provision, not product.** Above `900` (144px) nothing is referenced.
  Defining those steps costs nothing, and it means a layout token added later does not need a new
  primitive underneath it.

Three steps sit inside the used range and are pointed at by no spacing token: `19` (3px), `87`
(14px) and `250` (40px), the last of which line height uses. Leaving them out of the assignment is
deliberate, and it is what makes density move evenly. See below.

## How density works

Each density is a **distinct assignment** of the names to primitive steps. It is not a
multiplier, not a `transform: scale()`, and `Compact` is not `Comfortable` × 0.75.

The rule is simpler than a multiplier would be: **there is one shared set of values, and each
density starts one position further along it.**

This is where the skipped primitives come in. `19` (3px), `87` (14px) and `250` (40px) exist on the
primitive scale but are left out of the set the names are assigned from, because including them
would make some names move one position and others two. `spacing.none` is the one name that does
not move at all, since there is nothing below zero.

The set is not evenly spaced, and it does not need to be. What has to hold is that consecutive
members are one position apart, so `5xl` going 88 to 96 to 112px is as regular, in the terms that
matter here, as `md` going 12 to 16 to 20px.

### Corner radius

Same collection, same one-position-per-density behaviour:

{/* GEN:density-radius BEGIN - regenerate with pnpm generate:spacing-reference. Do not edit by hand. */}

| Token | Compact | Comfortable | Relaxed |
| --- | --- | --- | --- |
| `corner-radius.none` | 0px | 0px | 0px |
| `corner-radius.rounded` | 2px | 4px | 6px |
| `corner-radius.rounded-outer` | 3px | 5px | 7px |
| `corner-radius.pill` | 9999px | 9999px | 9999px |

{/* GEN:density-radius END */}

`rounded-outer` is not an independent value. It is defined as `rounded` plus 1px, so it follows
`rounded` at every density without being maintained separately. The plus-1px mirrors the 1px
`outline-offset` a focus ring uses in CSS, which is the only thing the token is for. See
[why not to reach for it](./spacing.mdx#corner-radius-travels-with-spacing).

## The cascade, end to end

```
spacing.md                     semantic     ← you use this
  → density.spacing.md         density      ← the active density supplies it
    → primitives.spacing.100   primitive    ← 16px
```

Three hops, one direction. A semantic spacing token never points at another semantic token, and
nothing points back up. In CSS the same chain is:

```css
--eds-spacing-md: var(--eds-density-spacing-md);
--eds-density-spacing-md: var(--eds-primitives-spacing-100);
--eds-primitives-spacing-100: 16px;
```

Bind to the first of those three. The density layer is an implementation detail of the density
switch, and the primitive layer is not published to the Figma picker at all.

## Adding a step

Two things a proposal has to answer.

1. **What relationship do the existing steps not express?** The case has to be about a pairing,
   not about one screen. "`sm` is slightly too tight here" is an argument for using `md`, not for
   a new name.
2. **What is the value in all three densities?** A new name needs one position in the shared set
   per density, which is what keeps it in step with everything else. At the low end that is the
   binding constraint, since Compact already starts at 1px.

Neither question is a bar against growth. Steps get added when the work reaches a scale the set
does not cover yet, and the layout end of the scale is where that happens: the steps above `3xl`
exist for page-level spacing, which is newer work than the components.
