# Storybook Component Docs

This is the canonical reference for how a component's page in the web Storybook is made, including its React Native tab. The page is generated by `scripts/generate-component-docs.js` from the component's code and a short hand-written file. This guide says what each part of the page is, who writes it, and what the generator enforces.

The usage guide on the Docusaurus site (`apps/design-system-docs`) has its own guide, [`COMPONENT_DOC_STYLE.md`](./COMPONENT_DOC_STYLE.md). The two do not overlap: Docusaurus answers when and why to use a component, Storybook answers how.

## How a page is made

| Input                              | Written by                        | Gives the page                            |
| ---------------------------------- | --------------------------------- | ----------------------------------------- |
| The `NameProps` type and its JSDoc | The developer, with the component | Features and the props                    |
| `Name.stories.tsx`                 | The developer                     | The examples and their captions           |
| `Name.docs.md`                     | A person, by hand                 | The parts code cannot tell us (see below) |
| `Name.figma.tsx`                   | The developer                     | The Figma link                            |

The generator combines these and writes the page. Never edit a generated file. It starts with a "Do not edit" comment, and CI fails if it no longer matches its inputs.

## Files

Everything for a component sits in the folder that holds `Name.tsx`. That is a folder of the same name on web (`next/Badge/`), and on mobile it can be a shared folder (`SelectionControls/` holds Checkbox, Radio and Switch).

| File                                                              | Web                        | Mobile              | Edit by hand |
| ----------------------------------------------------------------- | -------------------------- | ------------------- | ------------ |
| `NameProps` type or interface, in any non-test file of the folder | Yes                        | Yes                 | Yes          |
| `Name.stories.tsx`                                                | Yes, rendered by Storybook | Yes, never rendered | Yes          |
| `Name.docs.md`                                                    | Yes                        | Yes                 | Yes          |
| `Name.docs.mdx` (next to the component)                           | Generated                  | Not used            | No           |
| `docs/Name.mdx` in `eds-mobile-components`                        | Not used                   | Generated           | No           |

Mobile story files only supply example code. They are left out of the build and the npm package, and `tsconfig.docs.json` type-checks them, so a wrong prop in an example fails `pnpm types`.

## Page structure

Both platforms use the same sections in the same order, and the React Native tab sits under the same page as the React tab.

| Section            | Web                                        | Mobile           | Source                                                       |
| ------------------ | ------------------------------------------ | ---------------- | ------------------------------------------------------------ |
| Summary            | Above the tabs, shared                     | Not in the tab   | Hand-written, web file only                                  |
| Beta callout       | Above the tabs                             | Not in the tab   | Generated                                                    |
| Links row          | In the tab                                 | In the tab       | Generated                                                    |
| Features           | Required                                   | Required         | Generated from the props, plus optional hand-written bullets |
| Usage              | Required                                   | Required         | Install and import generated, snippet hand-written           |
| Props              | `Props and playground`, with live controls | `Props`, a table | Generated                                                    |
| Examples           | Required                                   | Required         | The stories file                                             |
| Accessibility      | Required                                   | Required         | Hand-written                                                 |
| Related components | Optional                                   | Optional         | Hand-written                                                 |

## The hand-written file

`Name.docs.md` holds what code cannot tell us. It has an optional metadata block at the top, then fixed sections:

````markdown
---
aria: https://www.w3.org/WAI/ARIA/apg/patterns/checkbox/
docs: inputs/selection_controls
---

## Summary

<!-- Notes to the author. Comments never reach the page. -->

What the component is, where it is used, and what to use instead when it does not fit.

## Features

- One bullet for behaviour the props do not show.

## Usage

```tsx
<Badge tone="success">Approved</Badge>
```

## Accessibility

- What the section must cover, see below.

## Related components

- [`Chip`](…) is the selectable counterpart.
````

| Part                           | Web file                                                    | Mobile file                                            |
| ------------------------------ | ----------------------------------------------------------- | ------------------------------------------------------ |
| Metadata `aria:`               | Optional, a `https://www.w3.org/` URL                       | Not used                                               |
| Metadata `docs:`               | Optional, only for a docs page shared by several components | Not used                                               |
| `## Summary`                   | Required                                                    | Rejected. The summary is written once, in the web file |
| `## Features`                  | Optional, required if the component has no props            | Same                                                   |
| `## Usage`, `## Accessibility` | Required                                                    | Required                                               |
| `## Related components`        | Optional                                                    | Optional                                               |

Any other heading, or any other metadata key, fails the generator. The metadata is not content and never renders as a section.

## Section rules

**Summary.** What the component is and where it is used, then what it is not for and what to use instead. It is shown on both tabs, so it must be true on both platforms. Anything that differs by platform goes in Features or Usage. Every component has one, with no length limit.

**Features.** An inventory of the API surface, not guidance. The generator writes one bullet per prop. A prop with a fixed set of values lists them with the default, `children` states its type, and any other prop uses its JSDoc description. Describe what each fixed value means in the JSDoc of the type, as one line per value:

```ts
/**
 * Visual emphasis level.
 * - `low`: Subtle background (canvas) or light border
 * - `medium`: More prominent fill or medium border
 */
export type BadgeEmphasis = 'low' | 'medium'
```

Add hand-written bullets in the file only for behaviour the props do not show, such as "Hidden from screen readers by default". Each component needs at least one bullet, generated or written.

**Usage.** One snippet showing the smallest correct use, without the import line. The generator adds the install command and the import.

**Props.** Generated from `NameProps`. Give every prop a JSDoc description and a `@default` tag where it has a default, because the page cannot show what the type does not say. Props inherited from a library, such as HTML attributes or `ViewProps`, are not listed.

**Examples.** Every component has at least one besides the playground story. On web the `Introduction` story is the playground and is not an example. Each export is one example, titled from its name (`InlineWithText` becomes "Inline with text"). Add a caption with `parameters.docs.description.story`. Write a caption only where it says something true for that platform.

**Accessibility.** Cover each of these that applies:

- the role the element exposes, or that it has none
- whether it can take focus, and which keys operate it
- what a screen reader announces, and what it does not, such as a tone shown by colour only
- what the consumer must supply, such as a label

The list names topics to cover, not a number of bullets. A component with seven things to say lists all seven, and one with two lists two. A component that is not interactive says so and says it is not focusable.

**Related components.** Leave the section out when nothing relates. Do not invent entries to fill it.

## Links row

| Link                  | Shown on                     | Source                                                                   |
| --------------------- | ---------------------------- | ------------------------------------------------------------------------ |
| GitHub source         | Each tab                     | The component's file path                                                |
| npm                   | Each tab                     | The package name                                                         |
| Figma                 | Each tab, when one exists    | The web `Name.figma.tsx`                                                 |
| Docusaurus design doc | Each tab, when a page exists | The docs-site page named after the component, or `docs:` in the metadata |
| WAI-ARIA pattern      | React tab only               | `aria:` in the metadata                                                  |

A component has one design doc across platforms. Add `aria:` only where a W3C pattern describes the component. A static element such as Badge has none, so it gets no link.

## Writing rules

- Use British English.
- Never use en or em dashes. The generator stops if one reaches a page.
- Write full sentences. Use a table or list for findings and comparisons.
- State only what the code or a test shows. Do not copy claims from older docs without checking them.
- Keep the story meta `tags: ['beta']`. The callout text is generated, so do not write it by hand.

## Commands

```bash
pnpm run generate:component-docs                 # every component with a hand-written file
pnpm run generate:component-docs Badge           # one component
pnpm run generate:component-docs --check         # exit 1 if a generated page is stale
```

CI runs the check before the build. After changing a type, a story or a hand-written file, regenerate and commit the pages in the same change.

## Not covered yet

- Components that exist only on mobile need their own Summary and a standalone page under `packages/eds-core-react/stories/mobile/`. The generator does not support them yet.
- The Foundation pages (Typography and Elements) are outside this outline.

## Checklist before committing

- [ ] The hand-written file has Summary (web only), Usage and Accessibility.
- [ ] Features has at least one bullet.
- [ ] There is at least one example besides the playground.
- [ ] Every prop has a JSDoc description, and a `@default` tag where it has a default.
- [ ] `pnpm run generate:component-docs --check` passes.
- [ ] No dashes and no unchecked claims in any text.
